# Organizer Guide (for organizers/admins, not participants)

`jb-sidequest` is a 2-use-case Julius Baer AI Hackathon. Use case 1 is an
AI agent challenge (payment investigation assistant requiring an LLM API
key, manually evaluated against a private answer key); use case 2 is a
retrieval + evidence-correlation problem (RAG-shaped, deliberately no
LLM, autoscoring via GitHub Actions on pull request). None require prior
domain experience beyond reading the brief. This doc covers the parts
participants don't need.

## Two evaluation models

| Use case | Evaluation | How to score |
|---|---|---|
| 1 — Payment Investigation Agent | Manual | Organizer runs `python main.py --questions questions.json --output submission.json` and evaluates `submission.json` against a private answer key (see `EVALUATION_CRITERIA.md`) |
| 2 — Production Incident Investigator | Automatic | GitHub Actions autoscoring on PR (6 weighted components via `scoring/cli.py`) |

The autoscoring engine (`scoring/`), CI workflow, and integrity
protection only apply to use case 2. Use case 1 has no `scoring_hooks.py`,
no `tests/`, no `benchmark/` — it's a separate paradigm.

## One-time repo setup (do this before sending participants the repo)

1. **Regenerate the protected-files manifest** after any change you make
   outside `submissions/`:
   ```bash
   python scripts/generate_protected_manifest.py
   git add scoring/PROTECTED_MANIFEST.json
   git commit -m "Regenerate protected manifest"
   ```
   **On Windows, do this only after `git add .gitattributes` has been
   committed at least once** (it already is, as of this repo's initial
   setup) **and never with `core.autocrlf=true`.** This repo hit a real
   bug during development: with autocrlf on, Windows silently rewrites
   checked-out text files to CRLF, so a manifest generated by hashing
   working-directory files no longer matches the LF bytes Git actually
   commits (and that Linux CI checks out) — every legitimate PR then
   fails integrity for a reason that has nothing to do with tampering.
   `.gitattributes` (`* text=lf`) forces LF on commit regardless of local
   config, which is what fixed it, but if you ever see integrity fail on
   a PR that clearly didn't touch protected files, check this first:
   `git show HEAD:<path> | sha256sum` (the true committed bytes) against
   the manifest entry, not `Get-FileHash`/`sha256sum` on a working-directory
   file, which can lie on Windows.

   Copy the sha256 it prints into the **`PROTECTED_MANIFEST_SHA256`
   repository variable** (Settings → Secrets and variables → Actions →
   **Variables** tab). This variable is **not set** in a fresh checkout —
   set it before the first real participant run. It's what makes the
   manifest file itself tamper-evident: the expected hash lives outside
   the git tree, so a PR can't edit both the manifest and the value it's
   checked against.

2. **Require branch protection on `main`**: require the `score` status
   check to pass, and require pull requests before merging.

3. **Require approval to run workflows from outside/first-time
   contributors** (Settings → Actions → General). **Not optional.**
   `scoring/integrity.py` stops a participant from scoring higher by
   editing protected files, but only a human approving the workflow run
   stops a PR that edits `.github/workflows/score-submission.yml` itself
   from running its own modified copy — GitHub's `pull_request` trigger
   uses the workflow file as it exists on the PR branch. Actually look at
   the "Files changed" tab for `.github/workflows/**` diffs before
   approving a run.

4. Decide how participants get access - a shared fork, or invite each as
   a collaborator. Either way, `scripts/setup_candidate_branch.sh` gets
   them a `submission/<name>` branch with their folder started (use case
   2 only — use case 1 has no `starter/` directory).

## Use case 1 — Manual evaluation setup

Use case 1 does not use the autoscoring engine. To evaluate:

1. Collect each participant's source code and `submission.json`.
2. Run `python main.py --questions questions/questions.json --output submission.json`
   in a fresh environment with only `pip install -r requirements.txt`
   plus the participant's chosen LLM SDK.
3. Evaluate the output against your private answer key using the rubric
   in `EVALUATION_CRITERIA.md` (answer correctness 40%, grounding/citations
   20%, tool usage 15%, RAG quality 15%, code quality 10%).

Participants need an LLM API key (any provider — see `.env.example`).
Make sure they know to bring their own key.

## Use case 2 — Autoscoring calibration

All `PERFORMANCE_THRESHOLDS` (in `scoring_hooks.py`) are first-pass
estimates, not independently benchmarked on your actual CI runner:

- **Use case 2**: `wall_clock_seconds` / `peak_memory_kb` for a single
  `investigate()` call over a padded corpus (base incident A's 7
  documents plus 5,000 extra synthetic log lines). Checks that retrieval
  scales reasonably with corpus size (e.g. a single TF-IDF fit, not a
  re-fit per document comparison) — the interesting difficulty in this
  use case is correctness/calibration, not raw speed, so this component
  matters less than correctness; don't over-tune it.

Write a quick correct reference solution (a TF-IDF-ranked,
multi-source-corroboration approach), run `python -m scoring.cli`
against it, and adjust `floor`/`target` in the relevant `scoring_hooks.py`
if your CI runner's numbers land somewhere you didn't expect.

## How scoring actually works (use case 2)

`usecase-2-production-incident-investigator/scoring_hooks.py` defines 6
weighted components (`correctness`, `performance`, `reusability`,
`code_quality`, `maintainability`, `completion` — see `scoring/cli.py`
for orchestration). By default `scoring/cli.py` never hard-fails CI
purely for a low score — it produces a report either way. Tampering (see
below) is the one thing that hard-fails unconditionally. If you want a
hard minimum, pass `--fail-under <score>` in the workflow's scoring step.

## Protecting the autoscoring engine (the mechanism)

Participants may only add new files under `submissions/<their-name>/`.
Everything else is hashed into `scoring/PROTECTED_MANIFEST.json`.
`.github/workflows/score-submission.yml` runs `python -m scoring.integrity`
as its very first step, before installing any dependency or touching a
submission - a PR that changed, deleted, or added a file outside
`submissions/` fails immediately, before the scoring engine ever runs.

Two known, deliberately-accepted limitations (proportionate to a
hackathon, not a paid competition):

- **Cross-participant protection is best-effort.** The manifest is a
  snapshot from when you last ran `scripts/generate_protected_manifest.py`
  — a previous participant's merged submission files aren't automatically
  re-protected until you regenerate again. Regenerate + commit after
  each merge if this matters for your process.

## Reporting across all participants

Per-PR autoscoring answers "does this one submission pass" — it doesn't
give you a roster. `scripts/generate_candidate_report.py` scans every
`submissions/<participant>/<usecase>/` folder present in your checkout,
re-scores each one with the same engine CI uses, and writes a
consolidated report:

```bash
git pull                                          # make sure you have every merged submission locally
python scripts/generate_candidate_report.py       # writes reports/latest/candidate_report.{md,csv}
```

`candidate_report.md` has one row per participant-per-use-case (total +
every component score) plus a "by participant" summary listing which use
cases each person attempted and their best score. `candidate_report.csv`
is the same data for pasting into a spreadsheet. Both are gitignored
(`reports/`) — this is a point-in-time report you generate on demand,
not something committed to the repo.

This only sees submissions that exist in your local checkout — `git pull`
first, and remember each participant's work lives on their own
`submission/<name>` branch until merged, so decide whether you're
reporting on merged submissions only (checkout `main`) or on everything
still open too (checkout each branch, or script a loop that does).

Note: `generate_candidate_report.py` only covers use case 2 (autoscoring).
Use case 1 results are evaluated manually — track those separately.

## Local dry run before sending this to anyone

```bash
pip install -r requirements.txt
python -m scoring.integrity                     # should print "Integrity OK"

./scripts/setup_candidate_branch.sh test-participant usecase-2-production-incident-investigator
# ... fill in the TODOs in submissions/test-participant/usecase-2-production-incident-investigator/ ...
python -m scoring.cli --usecase usecase-2-production-incident-investigator \
  --submission submissions/test-participant/usecase-2-production-incident-investigator
```
